> [!question] Проба 1 (реактивность)

Что именно делает `reactive({ a: { b: 1 } })` в Vue 3?

- Создаётся Proxy-обёртка; вложенные объекты становятся реактивными не сразу, а при первом обращении к ним
- Исходный объект глубоко копируется в новый реактивный объект
- Все вложенные объекты рекурсивно оборачиваются в Proxy сразу, в момент создания
- Свойства переопределяются через defineProperty, поэтому объект должен существовать заранее

> [!success] Проба 1

Выбран правильный вариант. ✓ `reactive` создаёт Proxy вокруг исходного объекта; вложенные объекты оборачиваются лениво — при первом чтении через get-ловушку. Глубокая рекурсивная обёртка не выполняется заранее.


> [!question] Проба 2 (реактивность, очередь обновлений)

В одном обработчике три раза подряд присваивается одно реактивное свойство (`count = 1; count = 2; count = 3`). Сколько раз Vue перерисует компонент?

- Три раза — каждое присваивание сразу запускает перерисовку
- Один раз — изменения складываются в очередь, рендер после завершения обработчика
- Ноль раз — рендер только при следующем изменении любых данных
- Три раза, но только если компонент не использует computed

> [!success] Проба 2

Выбран правильный вариант. ✓ Батчинг: обновления складываются в очередь, компонент помечается один раз (дедупликация по id), флаш очереди — в микротаске после обработчика. Отсюда назначение `nextTick`: после изменения данных DOM ещё не обновлён.


> [!question] Проба 3 (компоненты, v-model)

Что именно делает директива `v-model` на кастомном компоненте в Vue 3?

- Передаёт проп `value` и подписывается на событие `input`
- Привязывает `ref` на экземпляр дочернего компонента и пишет в его данные напрямую
- Сериализует значение в HTML-атрибут и синхронизирует его через DOM-события
- Передаёт проп `modelValue` и подписывается на событие `update:modelValue`

> [!success] Проба 3

Выбран правильный вариант. ✓ `v-model` на компоненте = `:modelValue` + `@update:modelValue`. Дистрактор «value + input» — дефолт Vue 2: разницу версий пользователь не путает.


> [!question] Проба 4 (рендеринг, key)

В `v-for` без `key` из середины списка удаляют элемент. Что произойдёт с уже существующими DOM-узлами?

- Узлы переиспользуются по позиции: каждый узел получает данные следующего элемента, лишний удаляется в конце
- Удаляется нужный узел, остальные нетронуты, потому что Vue сравнивает содержимое
- Узел удаляется, все остальные пересоздаются с нуля
- Vue определяет удалённый элемент по тексту и сдвигает узлы только при совпадении тегов

> [!success] Проба 4

Выбран правильный вариант. ✓ Без `key` сопоставление идёт по индексу: узлы переиспользуются по позиции, содержимое «съезжает», лишний узел удаляется в конце. `key` даёт Vue стабильную идентичность элемента для diff-алгоритма.


> [!question] Проба 5 (Vue Router 4, навигационные хуки)

В каком порядке выполняются навигационные хуки Vue Router 4 при обычном переходе?

- beforeEach → afterEach → beforeResolve
- beforeRouteEnter → beforeEach → afterEach
- beforeEach → beforeEnter → beforeRouteEnter → beforeResolve → afterEach
- beforeEach → beforeResolve → beforeEnter → afterEach

> [!failure] Проба 5

Выбран «beforeRouteEnter → beforeEach → afterEach». ✗ Правильный порядок: `beforeEach` (глобальный) → `beforeEnter` (маршрут) → `beforeRouteEnter` (компонент) → `beforeResolve` (глобальный, перед подтверждением) → `afterEach` (после подтверждения). Компонентный хук не может идти раньше глобального `beforeEach`. ✓/✗: порядок навигационных хуков — проба 1 (край: компонентный хук поставлен раньше глобального).


> [!question] Проба 6 (зондирование: назначение guard'ов)

Где лучше всего выполнить глобальную проверку авторизации с редиректом на `/login`?

- В beforeResolve — он выполняется последним перед подтверждением навигации
- В глобальном beforeEach — до резолва маршрута, отмена через next(false) или next('/login')
- В beforeRouteEnter компонента — там есть доступ к экземпляру компонента
- В afterEach — после перехода выполнить редирект на страницу входа

> [!failure] Проба 6

Выбран «В beforeRouteEnter компонента». ✗ Каноника — глобальный `beforeEach`: он срабатывает до резолва маршрута, и его достаточно зарегистрировать один раз. `beforeRouteEnter` — per-компонентная защита: дублируется в каждом компоненте, и доступа к `this` там нет (только `next(vm => ...)`). Вывод: заблуждение системное — пользователь привязывает guard'ы к компонентам, а не к глобальным хукам роутера; порядок хуков и их назначение не связаны в единую картину.

> [!abstract] Учитель

Край по реактивности не дострелян — в интервью поднимать сложность до промаха.

const { count } = state

> [!question] Вопрос 4 (watchEffect и асинхронность)

```js
const a = ref(1)
const b = ref(2)
watchEffect(async () => {
  const x = a.value
  await Promise.resolve()
  console.log(b.value)
})
a.value = 10
b.value = 20
```

Какие изменения заставят `watchEffect` сработать повторно?

- При изменении и `a`, и `b`: watchEffect трекает все обращения во время выполнения
- Только при изменении `a`: зависимости трекаются лишь до первого `await`, `b` уже вне отслеживания
- При изменении только `b`
- Ни при каких: watchEffect одноразовый, он не следит за изменениями


> [!question] Вопрос 4 (watchEffect и асинхронность)

```js

  const x = a.value
  await Promise.resolve()
  console.log(b.value)

```

Какие изменения заставят `watchEffect` сработать повторно?

- Только при изменении `a`: зависимости трекаются лишь до первого `await`, `b` уже вне отслеживания
- При изменении только `b`
- Ни при каких: watchEffect одноразовый, он не следит за изменениями

> [!failure] Ответ 4

Выбрано «При изменении и a, и b». ✗ Правильно — только при изменении `a`. Объяснение: чтение реактивного значения = подписка, но подписка оформляется на эффект, активный в момент чтения. Пока колбэк выполняется синхронно, `a.value` приписывает эффект в зависимости `a`. Первый `await` приостанавливает колбэк, глобальный «текущий эффект» сбрасывается — всё, что прочитано после (b.value), не трекается. Практика: нужные значения читать до `await` или использовать `watch` с явными источниками; в Vue 3.5+ — `onWatcherCleanup` для отмены запросов.

> [!success] Ответ (проверка)

## Блок 2. Компоненты и Composition API

> [!question] Вопрос 1 (жизненный цикл: порядок mounted)

```js

// Внутри родительского компонента

```

Что выведет консоль при первом рендере?

- `parent mounted`, затем `child mounted`
- В порядке объявления в исходниках
- `child mounted`, затем `parent mounted` — дети монтируются раньше родителя
- Порядок недетерминирован


> [!question] Вопрос 1 (жизненный цикл: порядок mounted)

- `parent mounted`, затем `child mounted`
- В порядке объявления в исходниках
- `child mounted`, затем `parent mounted` — дети монтируются раньше родителя
- Порядок недетерминирован

> [!failure] Ответ 1

Выбрано «parent mounted, затем child mounted». ✗ Правильно: дети монтируются раньше родителя. > [!question] Вопрос 1 (зачем Virtual DOM)

Зачем Vue нужен Virtual DOM? Почему нельзя просто менять DOM напрямую?

- Чтобы обновлять DOM быстрее, чем руками: VDOM-операции всегда быстрее реальных
- Чтобы получить декларативную модель: описываешь состояние, а минимальный набор DOM-патчей вычисляется системой
- Чтобы решить проблему кроссбраузерности: VDOM заменяет несовместимые DOM-API во всех браузерах
- Чтобы писать меньше кода: VDOM автоматически генерирует HTML, что упрощает парсинг

> [!failure] Ответ 1
